# 微信 MCP 操作手册：从界面识别到发送核验

面向连接 OpenGCUA 的其他 harness。本文讲的是如何根据当前界面决定下一步，不是固定次数的点击脚本。窗口位置、缩放、搜索结果、网络延迟都会改变调用次数。默认由调用方判断，OpenGCUA 直接执行；不要求调用方与 OpenGCUA 各运行一轮模型。

连接配置见 [CONNECT.zh-CN.md](CONNECT.zh-CN.md)，实际成功和失败记录见 [WORKFLOW.zh-CN.md 第 9 节](WORKFLOW.zh-CN.md#9-微信发送实测与其他-harness-复测)。以下工具名不含客户端前缀，参数以当前客户端发现的 schema 为准。

## 先明确任务和完成条件

开始前保留以下任务数据，而不是边操作边猜：

```text
mode = locate_only 或 send_once
target_name = 用户指定的完整联系人备注/群名
target_kind = contact 或 group
message = 用户授权的精确文本（仅 send_once 使用）
send_dispatched = false
```

例如本次成功案例的目标分别是联系人 `老婆` 和群 `聚聚群`。群名中的“群”是实际名字的一部分，不能擅自删掉。任务已有明确发送授权时不必重复询问；本手册和历史成功记录本身不是再次发送这两条消息的指令。

完成条件：定位任务须在主聊天区看到正确标题；发送任务还须看到本次新发出的本人消息，并核对内容及发送状态。工具调用返回成功、输入框清空、左侧列表置顶，单独任何一个都不足以证明发送成功。

## 按状态推进，不按固定步数推进

| 当前状态 | 需要看到的证据 | 下一步 |
| --- | --- | --- |
| 未附着微信 | 应用清单中的准确实例 | 选择主窗口并观察 |
| 主窗口可见 | 搜索框、会话列表、聊天区的实际布局 | 找到并聚焦搜索框 |
| 搜索框已聚焦 | 搜索框边框/光标等焦点证据 | 输入或替换搜索词 |
| 搜索词已输入 | 搜索框内容正确 | 查找搜索结果所在窗口 |
| 搜索结果已显示 | 结果分类、候选完整名称、头像 | 选择唯一匹配项 |
| 聊天已打开 | 右侧聊天标题与目标一致 | 定位任务结束；发送任务检查输入框 |
| 文本准备好 | 正确聊天标题、精确草稿 | 执行一次发送 |
| 发送已触发 | 已记录发送尝试 | 只核验，禁止重放发送 |
| 已核验或阻塞 | 消息证据或明确原因 | 释放会话并报告 |

每次观察先重新判断所处状态。例如已经在正确聊天中就不用再次搜索；搜索结果已出现就不用再次输入；消息已经发出就直接核验。观察可以重复，写入不能因为等待久就重复。

## A. 找到正确的应用和主窗口

1. 调用 `status({})`，记录 `host_pid`、`server_pid`、Dock 读数。只运行一个桌面操作任务。
2. 调用 `list_apps({})`，按 `native_id=com.tencent.xinWeChat` 查找微信，保存返回的 `apps[].id` 为 `app`。不能用历史 PID 拼出 ID，也不能在不完整清单里仅凭显示名称断言应用不存在。
3. 没有找到时先报告清单是否完整。若已确认未运行，可用调用方的应用启动能力打开原安装的微信，或明确委托 OpenGCUA 只做“打开微信”后重新列举；`observe` 不负责启动应用。遇到登录页，停止在登录环节，不把它当聊天窗口。
4. `list_windows({app})` 返回的“微信”窗口可能不止一个。依据标题和尺寸挑选候选，再调用 `observe({app,window_id,screenshot:true})` 确认：主聊天窗口应包含左侧导航栏、会话列表及右侧聊天区域。本次有 1000×700 点的主窗口和另一个 280×380 点的同名窗口；尺寸只是当次线索，不是筛选常量。
5. 保存确认后的 `main_window_id`。窗口关闭或重建后重新列举，不能靠旧编号继续输入。

本次 AX 树只有窗口和按钮，缺少搜索框、联系人及编辑区节点；这时采用截图。若其他版本提供了具名且可编辑的 AX 节点，可使用最新观察中的 `click`、`set_text` 等，但不能从截图顺序虚构元素编号。

## B. 从截图找到搜索入口，并确认焦点

在本次桌面布局中，搜索框位于**会话列表顶部、左侧导航栏右边**。它是横向圆角输入框，左侧有放大镜，空时显示“搜索”，右侧外面有一个圆形加号。它不是聊天区右上角的气泡/通话按钮，也不是聊天区底部的消息输入框。

识别后选择输入框内部的空白或文字区域，避开放大镜、清除叉号和加号，执行：

```json
{"view_id":"<最新主窗口视图>","image_id":"<该视图的截图ID>","x":216,"y":37}
```

这是 `click_image` 的**历史坐标示例**：当次主窗口截图为 1366×956 像素，搜索框大致在 x=100…350、y=20…57。实际复测必须重新看图选点，不直接执行这个坐标。

点击后检查动作返回的新截图，或重新 `observe`。本次搜索框获得焦点时出现绿色轮廓和插入光标；不同主题可能只显示光标或边框变化，不能只按颜色判断。搜索框的焦点证据应在搜索框内，不能把消息输入框里的光标误认为搜索已聚焦。

若没有焦点证据，不输入。重新观察是否被菜单/弹窗覆盖、窗口是否改变、点击位置是否正确。确定先前点击未聚焦且目标仍清楚时，可重新定位点击；不要对同一个旧坐标反复点击。

### 坐标和视图必须成对使用

- `click_image` 接收**返回图像的原始像素坐标**，不是屏幕绝对坐标，也不是窗口 bounds 中的 macOS 点坐标。
- 若客户端将原图缩放显示为 Wd×Hd，原图为 W×H，且没有裁切，显示位置 `(xd,yd)` 可换算为 `(xd*W/Wd, yd*H/Hd)`。裁切图要先补偿裁切偏移；无法确定就查看原图。
- 本次主窗口 1000×700 点对应 1366×956 像素，浮窗 368×674 点对应 736×1348 像素，不能统一乘 2，也不能把主窗口坐标用于浮窗。
- 每个动作使用最新 `view_id`，`image_id` 必须属于该视图。再次 `observe` 会使旧视图失效；不要先观察主窗口，再拿旧浮窗视图点击。

## C. 输入搜索词，处理已有文字

确认搜索框已聚焦之后：

- 空框：`type_text({view_id:最新视图,text_value:target_name})`。
- 已有相同搜索词：不再输入，直接检查结果。
- 已有其他搜索词：在确认搜索框焦点后，`press_key({view_id:最新视图,key:"a",modifiers:["cmd"]})` 全选，再用返回的新视图 `type_text` 替换。若截图显示焦点移到了聊天编辑区，立即停止，不能全选或清空聊天草稿。

`type_text` 会激活所绑定的准确窗口并输入，不会自动替调用方选中正确输入框。它返回 `effect:unknown` 时仍需检查效果。重新观察主窗口，确认显示的搜索词正确；如果输入没有出现，先检查当前焦点、已有内容及是否有弹窗，不直接再打一遍。

按完整目标名搜索优先于宽泛关键字。“老婆”的结果可能包含“柳棋老婆晶晶”；高亮匹配字样不代表全名相同。

## D. 找到搜索结果：重点检查独立浮窗

输入后调用 `list_windows({app})`，与输入前的清单比较。微信本次将结果放在一个**无标题独立窗口**里，它从搜索框下方展开，覆盖会话列表。主窗口截图不会把这个浮窗合成进去，所以“主窗口截图没结果”不等于“没搜到”。

候选浮窗的判断：新出现的无标题窗口、位置靠近搜索框、截图内包含搜索结果分类和条目。不能把所有无标题窗口都认定为结果。对候选执行 `observe({app,window_id:候选ID,screenshot:true})`，以内容确认。

如果没有新窗口：

1. 检查主窗口中关键词是否确实输入，是否已经出现内嵌结果；微信不同版本可能采用不同布局。
2. 若已输入且界面正在加载，可由客户端短暂等待（例如 0.5～1 秒），再列举/观察。等待是给界面刷新，不是重新输入的理由。
3. 在一个有上限的观察窗口内仍无结果（例如总计 10 秒，按实际环境配置），保存当前证据并报告，不无限循环。这个时限是建议保护值，不是微信响应保证。

**不要对搜索浮窗调用普通窗口激活。** 本次模型执行因此触发 `bring_to_front_window_not_ordinary` 并使它的设备会话离线。直接 MCP `click_image` 点击观察到的结果行已实测可用。

## E. 从结果中选择联系人或群

先读分类，再读条目完整名称：

- 联系人可能位于“最常使用”或联系人结果区域。寻找独立联系人条目；不要选聊天记录中包含该名字的消息。
- 群目标要选“群聊”区域的群条目。搜索“聚聚”时，本次上方先出现“搜索网络结果”及多个建议词；真正目标是下方“群聊”中的“聚聚群”。不能点顶部同名网络建议。
- 头像、群头像拼图是辅助线索，完整名字和目标类型才是必要条件。同名多个候选需用户消歧，不能凭排第一猜测。
- 目标不在可见区域时，只在明确相关分类中使用可见的“查看全部”或滚动；每次展开/滚动后重新观察。不要读取无关聊天记录来推断身份。

点击目标行中间的名称或空白区域，避开右侧“信息”按钮。使用当前结果截图的 `view_id`、`image_id` 和坐标。

本次历史示例（不能作为新会话的定位数据）：

| 结果截图 | 识别依据 | 当次选点 |
| --- | --- | --- |
| 736×1348，搜索“老婆” | 第二个联系人行全名为“老婆”，上面一行是其他全名 | `(238,279)` |
| 736×1348，搜索“聚聚” | “群聊”分类中唯一“聚聚群”行 | `(230,512)` |

点击结果通常关闭浮窗。若回执显示动作已分发，但后续观察报 `STALE_TARGET: window is closed`，先转到主窗口观察；不要再次点击那个位置。

## F. 确认打开的是目标聊天

`observe({app,window_id:main_window_id,screenshot:true})` 后查看右侧聊天区域顶部的标题。左侧选中行也可交叉核对，但仅列表高亮不能替代主聊天标题。

本次“老婆”标题在聊天区左上角，聚聚群标题显示为 `聚聚群 (16)`。只将明确表示成员人数的尾部部分作为附加信息，不任意去掉名称字符。完整标题不匹配、文字截断无法核实、同名歧义未解决时，不输入消息。

`locate_only` 模式到这里就完成。记录标题证据后收尾，不为了证明输入能力擅自发消息。

## G. 找到消息编辑区，准备精确文本

发送模式下，先记录发送前的底部消息状态，便于之后区分历史同文消息与本次新增消息。

消息编辑区位于**右侧聊天内容底部**，是较大的文本区域，底边有表情、附件等工具，右下角有“发送”按钮。它不同于左上角窄小的全局搜索框。本次编辑区大致在主截图 x=428…1348、y=738…939；点击 `(750,790)` 是当时的选点，复测仍须重新识别。

1. 检查是否已有草稿。空白才可直接输入；若已有用户草稿，不覆盖、不追加、不发送，报告草稿冲突。若恢复当前任务且草稿恰为本任务文本，也要结合本任务记录确认来源。
2. 点击编辑区的文本空白位置，避开表情/附件/麦克风和发送按钮。重新观察焦点。本次可见插入光标出现在编辑区左上方。
3. 用绑定主窗口的最新视图调用 `type_text({view_id,text_value:message})`，一次输入完整文本。中文、标点、空格按授权原文保留，不自行润色。
4. 重新截图，核对**聊天标题和输入框正文同时正确**。较长内容需确认完整正文，不能只检查开头。若出现 @成员选择菜单，先确认现在是普通文字还是实际成员提及流程；本次介绍里的 `@我` 是普通文字。
5. 若输入重复、截断或错字，不发送。只有能确定草稿完全属于本任务、尚未发出且焦点在该编辑区时，才可全选替换并再核验；否则报告，不能清空未知草稿。

## H. 发送一次，并区分三种结果

发送前保存当前任务的收件人、文本、发送前证据，将 `send_dispatched=true` 作为“发送即将尝试”的保守标记写入调用方任务记录，然后只执行一种发送动作：

- 已验证当前微信 Return 会发送时：`press_key({view_id:最新主窗口视图,key:"return"})`。这是本次实测使用的方式。
- 发送快捷键未知时：可以根据最新截图点击明确可用的“发送”按钮；这是建议替代路径，本次未用它发送。不要先按 Return 又点发送作为“双保险”。

如果 Return 只产生换行，停止并核对当前设置和草稿，不继续连按。标记只用于阻止自动重放，不声称这个布尔值就能提供跨崩溃的严格一次投递保证。

发送后只观察，检查以下证据：

| 结果 | 判断依据 | 处理 |
| --- | --- | --- |
| 客户端显示已发送 | 目标标题正确；相较发送前新增本人消息；正文匹配；未见发送中/失败标记；输入框清空作为辅助 | 报告已发送，不声称已读 |
| 明确发送失败/仍在发送 | 新气泡带错误标记、发送中状态或其他明确提示 | 如实报告或有界等待；不自动点重发 |
| 结果未知 | 超时、传输断开、截图失败、气泡被遮挡、无法区分历史同文消息 | 恢复只读观察和检查记录；不能自动重发 |

消息气泡本次在右侧、绿色、旁边是本人头像。颜色随主题可能改变，主要根据方向、本人身份和发送前后变化判断。不能只因聊天里已有一个 `test` 就认定本次成功；应结合新增位置、时间/前后截图、聊天列表摘要和调用记录。

发送状态不明确时，即使模型任务返回 `failed`，也不应重新提交整个发送任务。任务失败与消息是否已经发出是两件事。

## I. 常见中断的恢复位置

| 现象 | 恢复方式 |
| --- | --- |
| 主窗口看不到结果 | 先验证搜索词，再列出窗口检查独立浮窗 |
| 回车打开了名字相近的联系人 | 重新观察标题；不得发送，返回搜索并选择精确目标 |
| 选择结果后浮窗消失、观察报窗口关闭 | 转到主窗口核对标题，不重放点击 |
| 点击/输入回执 `effect:unknown` | 查新截图确认实际效果，不把它当明确失败重试 |
| `STALE_VIEW` | 重新观察目标获取新令牌，先确认前一个动作是否发生 |
| 浮窗激活错误导致 `DEVICE_OFFLINE` | 若为模型操作先停止并确认终态；释放自己的直接会话后重新建立观察，重新发现窗口；不要另起后台绕过 |
| `RESOURCE_BUSY` | 检查是谁持有桌面任务；不要抢占其他 harness，自己的模型任务确认结束后再操作 |
| 用户切换窗口或开始编辑 | 重新核对标题和焦点；检测到冲突就暂停输入，不追着焦点发送 |
| 发送动作后连接断开 | 保留发送已尝试标记，只读恢复核验；结果仍不明就报告，不自动再次发送 |

收尾调用 `release({})`、`status({})`，记录会话释放、宿主/工作进程复用、Dock 有效读数。只做首尾检查就只报告首尾结果。

## 给其他 harness 的入口提示词

把这份手册作为可读附件或提供其完整本地路径，不能只贴一个其他机器不可访问的路径。任务可以这样下达：

```text
先阅读 packages/mcp/WECHAT.zh-CN.md，使用当前连接的 OpenGCUA MCP。
这次任务：只定位并打开群“聚聚群”，不发送消息。
按实际界面状态推进，不按固定点击次数执行；搜索框焦点、独立结果浮窗、
候选完整名称、主聊天标题都要核验。使用当次截图和新 view_id，不复制历史坐标。
遇到错误先查动作是否已经发生，禁止盲目重放。完成后释放会话并报告证据。
```

若用户明确要求发送，将任务句替换成“向联系人/群〈完整名称〉发送一次〈精确文本〉”，其余检查保留。建议换用可区分历史消息的新测试文本。复测报告至少记录：客户端/harness、使用直接工具还是模型委托、目标完整名称、各阶段证据、异常与恢复方式、发送尝试次数、结果及首尾宿主/Dock 状态。调用次数随现场变化，不作为成功标准。
